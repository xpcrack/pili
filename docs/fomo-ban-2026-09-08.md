# FOMO 账号封禁事故复盘（2026-09-08）

## 结论速览

- fomo.family 唯一绑定账号 **inarius**（tracked_users 里 pow 的 fomo_handle）被封禁。
- 数据层损失 ≈ 0（管道 9-05 起已停，newone 从未接 agent API），停掉的是未来计划。
- 根因是**本仓库的 bug**，不是插件问题；已修复 + 加断路器止血。

## 根因链（日志实证）

```
插件(GemView) 正常推送新 JWT → pili-web-prod 写入 app_state.fomo_jwt (DB 一直是新的)
        ↓ 但
fomoClient.stateJwt() 有进程内缓存 (inMemoryJwt 非空即返回, 永不重读 DB)
        ↓ 导致
background-worker 进程(独立于 web-prod) 启动后缓存了旧 token, 过期后
以 45s/次 硬刷 "JWT 已过期"  →  9-03~9-07 四天, error 日志 7913 条, 日均 ~1900 次死 token 请求
        ↓
9-07 起 FOMO 上游开始 403 (日志 "FOMO 请求限流 (403)") → 9-08 账号被封
```

印证了 fomo-api-integration skill 里的旧结论：**过期 token + 密集请求的组合会触发封锁**。

## 已落地的修复

1. **`lib/server/fomoClient.ts`**
   - 401 时 `setInMemoryJwt(null)`：进程内 JWT 缓存失效，下轮强制重读 DB（根因修复）。
   - 断路器 `PILI_FOMO_CIRCUIT_OPEN=1`：`apiCall()` 在任何检查之前短路抛
     `circuit_open`，连 admin 手动触发也发不出上游请求。
2. **`server/runtime-tasks.ts`**
   - 总闸 `PILI_FOMO_TASKS_DISABLED=1`：fomo-trades / fomo-positions / fomo-stats /
     fomo-identity-sync 四个任务全部空转（sleep 10min~1h，status=idle）。

开关写在 `pilipili/.env.local` 尾部，带注释。

## 经验教训（泛化）

- **"短效 token + 进程内缓存 + 多进程" 是雷**：写方（web 进程收插件推送）和读方
  （worker 轮询）不是同一进程时，读方的缓存必须有失效机制（401 清缓存 / TTL）。
- **错误日志每天 ~1500 条同一条消息持续 4 天 = 有人在硬刷死凭据**，应该在出现
  第一批 jwt_expired 时就熔断，而不是让循环空转到上游动手封号。
- 数据管道的下游消费者为 0 时（newone 没接 agent API），停摆 10 天无人察觉——
  接新管道时先接消费者，再谈轮询频率。
