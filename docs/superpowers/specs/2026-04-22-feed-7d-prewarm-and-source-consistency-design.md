# Feed 7 天预补齐与多源一致性设计

日期：2026-04-22  
状态：草案（已在 brainstorming 过程中确认）  
负责人：Feed pipeline

## 1. 背景与问题
当前行为在“选中单人并补历史”时会阻塞切人。实际表现是：用户点击人物 B，但右侧长时间仍显示人物 A 的 feed。该问题在本地库数据偏薄时会被明显放大。

同时，时间线数据来自多源：
- Twitter：TG 转发 + OpenCLI
- 链上交易：TG 转发 + API
- TG 渠道仅监听，无法回溯

对于同一事件/同一时间窗，不同来源经过解析后的产物必须一致。

## 2. 目标与非目标
目标：
- 实现“秒切”：切换人物不等待补历史。
- 启动后自动后台补齐最近 7 天。
- 顶部轻量进度展示：`补齐中 x/y 地址（近7天）`，完成后显示完成状态。
- 建立多源归一化一致性与确定性冲突收敛规则。
- 冲突通过系统内置 tgbot 实时逐条推送到指定 TG 群。

非目标：
- 本期不做 30/90 天扩展补齐。
- 不做重弹层或强打断式提醒交互。
- 不尝试对 TG 监听源做历史回补（能力上不可行）。

## 3. 已确认产品决策
- 覆盖目标：最近 7 天。
- 触发方式：应用启动后自动后台预补齐。
- 进度展示：顶部轻量状态。
- 冲突默认胜出源：
  - 链上：API 优先。
  - Twitter：OpenCLI 优先。
- 冲突告警：逐条实时推送，不做聚合。
- 设置项新增：用于冲突通知的 Telegram 群 Chat ID。

## 4. 总体架构
### 4.1 为“秒切”做前后台解耦
- 前台查询链路采用“本地快照优先”，不等待 backfill。
- 后台预补齐/补历史采用独立任务通道与状态机。
- 切人时必须可抢占：旧用户的深度补历史请求可被中断或降级为后台继续，不得阻塞新用户展示。

### 4.2 7 天时间线预补齐
- 启动时调度全局预补齐任务。
- 任务按“由近到远”推进，直到 `earliestCoveredAt <= now - 7d`。
- 每步成功后持久化时间窗游标与检查点，避免重复扫描。
- 每轮增量写入快照后，前台轮询可立即读到新增数据。

### 4.3 统一 Canonical 归一化
所有来源统一映射到同一 canonical schema 与同一展示元数据管道。
对于等价事件，禁止按 source 走不同展示逻辑。

Canonical 主键要求：
- 链上：`chain + trackedAddress + txHash + signature(token/action/amount)`
- Twitter：`tweetId`（回复/引用采用统一归一化规则）

## 5. 多源对账与一致性保障
### 5.1 来源角色定位
- TG 转发：先到达的实时监听快照。
- API/OpenCLI：可回溯的对账来源。

### 5.2 对账规则
当两个来源命中同一 canonical identity：
- 若归一化后字段一致：仅合并来源足迹（source footprint），不改业务字段。
- 若字段不一致：创建冲突记录（字段级 diff），并按策略收敛：
  - 链上 => API 为最终 canonical。
  - Twitter => OpenCLI 为最终 canonical。

### 5.3 一致性指标
按域分别统计并暴露：
- `match_rate`
- `mismatch_rate`
- 当前预补齐窗口冲突数

## 6. 冲突通知设计
### 6.1 设置项
新增设置字段：
- `conflictNotificationTelegramChatId`（字符串）

行为：
- 已配置：每条冲突实时推送。
- 未配置：仅落库记录冲突日志，并在设置页提示“未配置通知群ID”。

### 6.2 消息契约
每条冲突通知包含：
- 事件时间
- canonical 事件主键
- 事件域（链上/Twitter）
- 来源 A / 来源 B
- 冲突字段列表
- 最终采用来源

### 6.3 去重与重试
- 去重键：`canonical_key + diff_signature`
- 同一冲突仅推送一次，避免刷屏。
- 发送失败按指数退避重试（例如最多 3 次）。
- 重试仍失败：落地待补发队列，后续再发。

## 7. 状态机
### 7.1 预补齐任务状态
`idle -> running -> partial|done`
- `partial`：部分地址失败，但整体继续推进。
- `done`：7 天边界覆盖完成。

### 7.2 前台读取状态
前台列表渲染不依赖预补齐状态推进。  
前台读取失败仅影响当前提示，不得锁死切人能力。

## 8. 错误处理
- 单地址失败不导致全局预补齐任务终止。
- 冲突推送失败不阻塞冲突收敛。
- 快照读取失败不阻塞继续切换到其他人物。

## 9. 测试策略
单元测试：
- canonical key/signature 生成
- 同样本双源归一化结果一致性
- 冲突判定与胜出策略
- 冲突去重键生成

集成测试：
- 启动预补齐进行中反复切人
- in-flight backfill 下前台秒切
- mismatch 触发实时 Telegram 推送
- 推送重试与待补发队列行为

回归测试：
- feed 渲染/搜索/筛选
- 拉取更多行为
- 诊断与进度统计展示

## 10. 验收标准
- 预补齐进行中切人仍为秒切。
- 顶部持续显示 7 天补齐轻量进度，完成后显示完成态。
- 同事件双源可确定性收敛到唯一 canonical 产物。
- 每个唯一冲突都向已配置 TG 群实时推送一条消息。
- 若未配置群 ID，冲突可查询且设置页有明确引导。

## 11. 下一步实施计划范围
后续 implementation plan 应拆成可并行的独立工作流：
1. 请求状态抢占与前后台通道拆分。
2. 7 天预补齐调度与检查点持久化。
3. Canonical 对账与冲突仓储。
4. 设置页与配置持久化（冲突通知群 ID）。
5. 通知集成、去重、重试与待补发。
6. 顶部进度 UI 与可观测指标。
