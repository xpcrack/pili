# Pilipili 运行时轻量化设计

生成日期：2026-05-20
范围：常驻运行模式、`pm2` 进程编排、开发/生产切换、后台 worker 低占用策略

---

## 一句话结论

**不改功能、不改页面体验，先把 `pili` 从“长期开发态运行”改成“产品态常驻运行”。**

核心做法只有三件：

1. 日常常驻的网页服务从 `next dev` 改为 `next build + next start`
2. 用 repo 内固定的 `pm2` 配置定义生产态 / 开发态切换规则，让 AI 可直接代操作
3. 保留现有 worker 功能与实时性，但增加运行护栏，避免 CPU 空转和内存长期膨胀

---

## 背景

当前 `pili` 作为个人长期常驻工具使用，但运行形态仍然接近开发机模式：

- Web 服务长期运行在 `next dev`
- Telegram / completeness worker 长时间驻留
- 用户主要通过 AI 操作项目，希望切换运行模式时不需要记命令

最近观测到的运行时症状：

- `next-server` 和 `telegram-channel-worker` 长时间占用数 GB 级内存 footprint
- 空闲时机器仍明显发热
- CPU 高负载不仅来自业务逻辑，也来自开发态缓存、系统压缩内存、长期不释放的 worker 状态

用户目标很明确：

- **功能不变**
- **体验不变**
- **实时性基本不变**（关键路径维持 5-15 秒级）
- 在此前提下尽可能降低常驻 CPU / 内存 / 发热

---

## 非目标

这次设计**不包含**以下内容：

- 不删功能，不改变现有页面交互
- 不重做业务流程，不重写 Telegram / completeness 主逻辑
- 不做“大整理式”代码重构
- 不要求把所有后台任务改为完全按需启动
- 不引入额外外部基础设施（消息队列、Redis、独立调度器等）

这是一轮**运行层优化**，不是产品改版。

---

## 设计目标

### 1. 日常模式必须稳定且轻量

日常运行应固定为：

- `production web`
- `telegram-channel worker`
- `completeness maintenance worker`
- 其他必要 worker（若已有常驻用途）

这套模式要能长期常驻，空闲时尽量低功耗。

### 2. 改代码模式必须简单到一句话触发

用户只会通过 AI 操作项目，因此“切开发态”和“切回生产态”必须成为项目内建规则，而不是人工记忆。

理想交互：

- “我要转开发态改代码了”
- “改完了，切回生产态”

AI 应该能根据 repo 内文档和配置直接完成切换。

### 3. 数据和账号状态必须共用

生产态与开发态都必须默认复用同一套：

- `.env.local`
- `.data/`
- SQLite 数据库
- Telegram session

不允许要求用户复制数据、迁移数据库、重新登录 Telegram。

---

## 方案概览

### 方案 A：推荐方案

**生产态常驻 + `pm2` 双模式切换 + worker 运行护栏**

优点：

- 最符合当前使用习惯
- 对功能和体验影响最小
- 收益最大的是去掉长期 `next dev`
- 便于 AI 自动化操作

缺点：

- 需要把运行规则正式写入 repo
- 需要增加少量运维脚本 / `pm2` 配置

### 方案 B：热路径 / 冷路径进一步拆分

优点：

- 资源下降可能更明显

缺点：

- 超出这次“体验不变”的范围
- 更容易引入调度复杂度

### 方案 C：只加自动重启和内存保险丝

优点：

- 改动最小

缺点：

- 只能缓解，不能解决 `next dev` 常驻的根因
- 对 AI 切换模式帮助有限

**结论：采用方案 A。**

## 运行模式设计

### 日常模式（默认）

默认常驻模式定义为：

- `web-prod`: `next build` 产物 + `next start --port 3005`
- `telegram-channel-worker`
- `completeness-maintenance-worker`
- 其他当前确认为常驻必需的 worker

禁止在日常模式下长期运行 `next dev`。

### 开发模式

开发模式不是整套系统都切换，只切换 web：

- 停止 `web-prod`
- 启动 `web-dev`（`next dev --port 3005`）
- 保持现有 worker 不变，除非用户明确要求

这样可以保证：

- 页面端代码修改仍有开发态体验
- 后台实时同步不中断
- 数据源和数据库仍连续

### 切回生产模式

从开发模式返回日常模式时，固定步骤为：

1. 停止 `web-dev`
2. 执行生产构建
3. 构建成功后启动 `web-prod`
4. 若构建失败，不切回生产态，并把失败原因明确反馈给用户

## `pm2` 编排设计

### 为什么必须引入 repo 内 `pm2` 配置

当前项目里没有 repo 内 `pm2` 配置文件，AI 无法可靠知道：

- 哪个 pm2 进程名对应哪个职责
- 哪些进程切换模式时该动，哪些不该动
- 启动命令是否带特殊环境变量

因此必须把进程拓扑固化到项目里。

### 进程命名约定

建议固定如下命名：

- `pili-web-prod`
- `pili-web-dev`
- `pili-telegram-channel-worker`
- `pili-completeness-worker`
- 其他后续确认为常驻的 worker，也统一以 `pili-` 前缀命名

### `pm2` 配置原则

- `web-prod` 和 `web-dev` 不能同时常驻
- 两者必须共享相同工作目录、`.env.local`、`.data/`
- worker 进程默认独立定义，不依赖 web 模式
- `web-prod` 使用 `npm run start`
- `web-dev` 使用 `npm run dev`
- worker 保持使用现有 `npm` scripts 启动，避免命令漂移

### AI 操作入口

为避免 AI 自己拼接复杂 `pm2` 命令，建议在 repo 内额外提供极薄的一层脚本或 npm scripts，例如：

- `npm run runtime:dev:on`
- `npm run runtime:dev:off`
- `npm run runtime:status`

它们内部再调用 `pm2`，让 AI 只需要调用稳定入口，而不是直接自由发挥。

## AI 协作规则设计

### 写入 `AGENTS.md` 的背景说明

项目需要增加一段明确的运行说明，告诉后续 AI：

- 这个项目日常由 `pm2` 常驻运行
- 默认模式是生产态 web，不是开发态 web
- 用户是非专业开发者，依赖 AI 帮忙切模式
- “切开发态”只切 web，不默认碰 worker
- “切回生产态”必须先 build，再恢复生产态 web

### AI 切开发态规则

当用户表达类似以下意图时：

- “我要转开发态改代码了”
- “帮我切到开发态”
- “先开 dev 我要改页面”

AI 应执行：

1. 确认并停止 `pili-web-prod`
2. 启动 `pili-web-dev`
3. 保持 worker 不变
4. 向用户报告当前模式

### AI 切回生产态规则

当用户表达类似以下意图时：

- “改完了切回生产态”
- “恢复日常模式”
- “回到常驻模式”

AI 应执行：

1. 停止 `pili-web-dev`
2. 执行生产构建
3. 若构建通过，启动 `pili-web-prod`
4. 若构建失败，保持非生产态并向用户说明原因

### AI 默认不要做的事

- 不要在未说明的情况下重启所有 worker
- 不要改 `PILIPILI_DB_PATH` / `PILIPILI_DATA_DIR`
- 不要为了切模式复制数据库
- 不要要求用户重新登录 Telegram

## 数据共享设计

当前项目已经具备共享基础：

- SQLite 默认位于 `.data/web3-feed.sqlite`
- 环境变量默认来自 `.env.local`
- 多个脚本通过 `process.cwd()` 解析工作目录

因此本次设计的原则是：

- 开发态与生产态必须继续共用当前 repo 的 `.data/`
- 开发态与生产态必须继续共用当前 repo 的 `.env.local`
- 不引入单独的“生产数据库”或“开发数据库”概念

这保证切换模式只影响运行形态，不影响数据连续性。

## Worker 轻量化设计

### 1. `telegram-channel-worker`

这是当前第二个主要高占用来源。目标不是降低功能，而是降低长期运行成本。

保留不变：

- 现有同步职责
- 关键路径实时性
- 数据写入与后续 completeness 触发关系

调整方向：

- **运行护栏**：增加明确的内存上限意识，而不是放任长期膨胀
- **平滑重建**：允许在安全边界内按条件重启 worker，避免一个进程无限跑到 4-5G footprint
- **资源释放检查**：梳理每轮同步结束后的连接、客户端、临时集合、批量结果对象，确保生命周期清晰
- **pm2 策略托管**：把自动拉起、重启策略交给 `pm2`，不要靠人工兜底

### 2. `completeness-maintenance-worker`

这个 worker 当前方向基本正确：

- 默认是低频巡检
- 已有 poke 驱动
- 空闲时并非高频扫描

本次只做运行层确认：

- 保持其“后台维护型”定位
- 避免与实时 worker 抢资源
- 不为追求一致性而提升到高频常热模式

### 3. 其他后台任务

若后续发现还有其他长期驻留脚本，需要按同一原则分类：

- 实时型：强调低延迟，但必须有内存护栏
- 维护型：强调低频、低优先级、空闲优先

## 验证标准

### 功能与体验验收

以下行为必须保持不变：

- 页面访问方式不变
- 数据源不变
- Telegram 登录状态不变
- 关键同步链路仍保持近实时

### 运行时验收

成功标准：

- 日常常驻时不再使用 `next dev`
- 空闲时 CPU 占用明显低于当前状态
- Web 进程内存不再表现出开发态长期膨胀特征
- Worker 长时间运行时，footprint 增长受到约束
- 机器空闲发热明显减轻

### 操作体验验收

成功标准：

- 用户可以通过一句自然语言让 AI 切到开发态
- 用户可以通过一句自然语言让 AI 切回生产态
- AI 不需要用户手动解释 pm2 进程名

---

## 风险与回退

### 主要风险

1. 生产态 web 与开发态在少数细节上行为不完全一致
2. 构建失败会阻断“切回生产态”流程
3. worker 的内存问题如果涉及第三方库内部状态，仅靠浅层护栏可能不够

### 回退策略

- 若生产态 web 出现重大兼容问题，可临时恢复到旧的开发态 web 运行方式
- 若某个 worker 的护栏策略带来稳定性问题，应优先回退该护栏，而不是回退整个运行模式设计
- 所有切换脚本都应保持可逆，避免单向迁移

---

## 分阶段建议

### Phase 1：先落运行模式

- 增加 repo 内 `pm2` 配置
- 增加运行模式切换脚本 / npm scripts
- 更新 `AGENTS.md` 与运维说明
- 先把日常 web 切出 `next dev`

### Phase 2：再加 worker 护栏

- 为 `telegram-channel-worker` 增加内存 / 重启策略
- 验证长时间运行下的 footprint
- 确认 completeness worker 仍维持低热状态

### Phase 3：最后做监测与微调

- 对常驻模式下的 CPU / 内存占用做一次复查
- 根据真实观测微调策略，而不是预先过度设计

---

## 结论

这次运行时轻量化的关键不是“砍功能”，而是**把 `pili` 从开发期运行方式切换到长期常驻产品运行方式**。

优先顺序很明确：

1. 先消灭日常 `next dev` 常驻
2. 再把开发 / 生产模式切换规则写进 repo，方便 AI 代操作
3. 最后给高风险 worker 增加内存与重启护栏

这样最符合当前目标：**功能不变，体验不变，但常驻更轻、更凉、更稳。**
