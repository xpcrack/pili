# 24 小时网络流量分析 + AI 智能分流方案

## 背景

- Clash Verge 混合端口: 7897
- 当前状态: TUN 模式开启（所有流量走代理），微信很慢
- 目标: 关闭 TUN，改为系统代理模式 + 精确的 per-domain 分流规则
- 项目外部依赖域名:
  - `api.telegram.org` (Telegram Bot API / MTProto)
  - `ai.6551.io` (Twitter 数据代理)
  - `65.109.123.54` (xread Twitter 代理，直连 IP)
  - `web3.okx.com` / `www.okx.com` (OKX Web3 API)
  - `api.mainnet-beta.solana.com` (Solana RPC)
  - `api.dexscreener.com` (DEX Screener)
  - `gmgn.ai` (GMGN)
  - `x.com` / `t.co` (Twitter，通过 6551 或 xread 间接访问)
  - `api.dicebear.com` (头像)
  - `pbs.twimg.com` (Twitter 图片)

## 方案概述

分三阶段:
1. **采集** — 写一个网络请求拦截器，记录 24h 所有出站请求
2. **分析** — AI 分析日志，分类域名，测试延迟
3. **落地** — 生成 Clash Verge 分流规则，关 TUN，开系统代理

## Phase 1: 网络请求采集

### 方案: 创建 logging proxy 层

在 `global-agent` 基础上加日志记录，不改变项目代码。

#### 1.1 创建 `scripts/proxy-with-logging.cjs`

功能:
- 用 `global-agent` bootstrap 拦截所有 HTTP/HTTPS 请求
- 同时用 `undici` 的 `ProxyAgent` 做实际代理转发到 `127.0.0.1:7897`
- 每条请求记录到 SQLite (复用项目的 `data.sqlite`)

记录字段:
```
timestamp    — ISO 时间戳
domain       — 目标域名 (如 api.telegram.org)
ip           — 解析后的 IP (如果能拿到)
port         — 目标端口
method       — GET/POST/etc
url          — 完整请求路径
status_code  — 响应状态码 (0 = 连接失败)
latency_ms   — 请求耗时
error        — 错误信息 (如果失败)
proxy_used   — 是否走了代理 (此时全部 true)
bytes_out    — 请求体大小
bytes_in     — 响应体大小
```

#### 1.2 创建 `scripts/start-logging.sh`

启动脚本，设置环境变量 + 启动 Next.js:
```bash
export HTTP_PROXY=http://127.0.0.1:7897
export HTTPS_PROXY=http://127.0.0.1:7897
export PROXY_LOG_ENABLED=1
NODE_OPTIONS='--require ./scripts/proxy-with-logging.cjs' npm run dev
```

#### 1.3 创建 SQLite 表 `network_request_log`

在 `data.sqlite` 中新建表，24h 后数据量预估: 几千到几万条，SQLite 完全够。

#### 1.4 同时补充测试: 无代理直连测试

写一个 `scripts/probe-direct-connectivity.ts`，测试每个域名:
- 直连是否可达 (不走代理)
- 直连延迟
- 走代理延迟

这个不需要 24h，跑一次就行（几分钟）。

## Phase 2: AI 分析

### 2.1 导出分析数据

创建 `scripts/analyze-network-logs.ts`:
- 按域名聚合: 请求次数、平均延迟、P99 延迟、错误率
- 分类:
  - **必须代理**: 直连超时/被墙的域名 (如 x.com, api.telegram.org)
  - **可以直连**: 国内可达且延迟低的域名 (如 okx.com 如果有国内 CDN)
  - **可选**: 都能通，但某条路径更快
- 按时间段分析: 高峰期 vs 低谷期的延迟差异

### 2.2 延迟对比测试

`scripts/probe-node-latency.ts`:
- 对每个"可选"域名，测试各节点 (台湾、新加坡、日本、美国、香港) 的延迟
- 输出推荐节点

### 2.3 生成分析报告

输出 JSON + 可读文本:
```json
{
  "domains": {
    "api.telegram.org": { "category": "proxy_required", "recommended_node": "🇸🇬 狮城节点", "reason": "直连超时" },
    "web3.okx.com": { "category": "direct_ok", "latency_direct": 45, "latency_proxy": 180, "reason": "国内CDN，直连更快" },
    "api.dexscreener.com": { "category": "proxy_recommended", "recommended_node": "🇯🇵 日本节点", "reason": "直连偶尔超时，日本节点延迟最低" }
  }
}
```

## Phase 3: 落地 Clash Verge 规则

### 3.1 生成 extend.yaml

Clash Verge 支持通过 `verge.yaml` 的 `override` 或直接编辑 `clash-verge.yaml` 来追加规则。但我们不应该直接改自动生成的文件。

方案: 在项目的 `clash/` 目录下生成规则片段，用户手动或脚本追加到 Clash Verge。

生成文件: `clash/project-rules.yaml`
```yaml
# pilipili 项目分流规则 (由 AI 分析生成)
# 必须代理
- DOMAIN-SUFFIX,api.telegram.org,🚀 节点选择
- DOMAIN-SUFFIX,x.com,🚀 节点选择
- DOMAIN-SUFFIX,t.co,🚀 节点选择
- DOMAIN-SUFFIX,ai.6551.io,🚀 节点选择
- DOMAIN-SUFFIX,api.dexscreener.com,🚀 节点选择
- DOMAIN-KEYWORD,twitter,🚀 节点选择
# 直连
- DOMAIN-SUFFIX,okx.com,DIRECT
- DOMAIN-SUFFIX,gmgn.ai,DIRECT
# 节点优选
- DOMAIN-SUFFIX,api.mainnet-beta.solana.com,🇸🇬 狮城节点
```

### 3.2 安装脚本

`scripts/install-clash-rules.sh`:
- 读取 `clash/project-rules.yaml`
- 注入到 Clash Verge 的 `clash-verge.yaml` rules 段
- 备份原始配置
- 提示用户重启 Clash Verge

### 3.3 最终使用方式

1. 用户在 Clash Verge 中关闭 TUN，开启系统代理
2. 用 `npm run dev:proxy` 启动项目 (已配置好)
3. 微信不受影响

## 使用流程

```
Step 1: npm run dev:proxy          # 启动带日志的开发服务器
Step 2: 正常使用 24 小时           # 采集数据
Step 3: npx tsx scripts/analyze-network-logs.ts   # 分析
Step 4: AI + 用户一起 review 分析结果
Step 5: bash scripts/install-clash-rules.sh       # 安装规则
Step 6: Clash Verge 关 TUN，开系统代理
Step 7: npm run dev:proxy           # 验证一切正常
```

## 风险 & 注意

- Telegram MTProto (gramjs) 用原生 TCP，不受 global-agent 控制。如果 Telegram 频道同步在系统代理模式下失败，需要单独处理 (可选: 给 Telegram 域名加 Clash 规则)
- `65.109.123.54` (xread) 是直连 IP，不经过域名解析，需要用 IP-CIDR 规则
- Clash Verge 的 `clash-verge.yaml` 是自动生成的，每次保存配置会覆盖。规则注入需要通过 Clash Verge 的 "Merge" 功能或编辑订阅源
- 24h 采集期间建议正常使用项目，让数据覆盖各种场景 (同步、刷新、搜索等)
